# 벤치마크 신뢰성 개선 보고서 — 2026-09-05

이번 작업은 XBEN-020의 접속 실패를 출발점으로, 벤치마크 실행·정리·증거 수집·통계 산출에서 확인한 결함을 수정한 기록이다. 목적은 에이전트의 실제 문제 해결 능력과 실행 장치의 오류를 구분하고, 다른 에이전트가 같은 현상을 반복해서 인프라 장애로 보고하지 않도록 만드는 것이다.

코드 수정과 회귀 검증은 완료했다. 진행 중인 벤치마크에는 개입하지 않았으며, 새 이미지 빌드나 104개 실벤치마크 재실행은 하지 않았다. 따라서 이 문서는 **구현과 테스트로 확인한 개선**을 설명한다. 실제 정답률 상승이나 모든 실행 환경의 무결성을 입증하는 보고서는 아니다.

## 1. XBEN-020: 포트가 없다는 보고의 실제 원인

### 증상과 원인

최초 보고는 `BENCHMARK_START_FAULT: no published port; cannot reach target from host`였다. 이 메시지만 보면 compose에 포트 발행을 추가하면 될 것처럼 보인다. 하지만 조사한 구성에는 공개 앱 `ssrf-demo-app`의 `ports: ["80"]`가 이미 있었다. 내부 서비스 `internal-service`는 `expose: ["80"]`만 사용하고 있었다.

`ports`는 호스트에서 접속할 포트를 발행한다. `expose`는 내부 네트워크에서 사용할 포트를 나타내며 호스트 포트 발행과 다르다. 이 문제에서는 내부 서비스를 외부에 직접 노출하지 않는 것이 SSRF 과제의 경계다.

기존 탐색은 서비스 목록에서 인프라 이름으로 분류되지 않은 첫 서비스를 선택했다. `internal-service`가 먼저 나오면 공개 앱 대신 내부 서비스를 타깃으로 지정했다. 호스트에서 실행하는 Claude 러너는 이 서비스에 도달하지 못했다. 컨테이너 네트워크를 사용하는 러너에서는 내부 서비스에 직접 도달해 의도한 문제 경로를 건너뛸 위험도 있었다.

### 변경 내용과 이유

세 러너가 공통 타깃 선택 로직을 사용하도록 했다. 실제 compose 상태에서 유효한 공개 TCP 포트를 가진 앱을 우선 선택한다. 포트가 UDP인지, 범위가 유효한지, 선택한 서비스의 실제 상태 행이 존재하는지도 확인한다. 내부 포트가 8080인 경우에는 그 값을 보존한다.

compose 실행 실패, 손상된 JSON, 필요한 상태 행 누락을 정상 타깃처럼 처리하지 않는다. 탐색 오류에는 `BENCHMARK_TARGET_DISCOVERY` 코드를 부여하고 시작 장애로 분류한다. 상태 행 자체가 없는 경우 임의의 `unknown:80` 주소를 만들지 않는다.

**XBEN-020의 내부 포트를 공개하는 suite 패치는 추가하지 않았다.** 그것은 잘못된 타깃 선택을 숨기면서 과제의 접근 경계를 바꾼다. 이번 원인에 맞는 수정 위치는 러너다. 기존 patch-suite의 EOL 저장소·phantomjs·compose 문법 보정 등은 별도 빌드 호환성 처리이며 이번에 모두 새로 만든 기능이 아니다.

### 확인 방법과 후속 조치

서비스 순서를 뒤집은 경우, JSON 배열과 NDJSON, DB 서비스 혼재, UDP, 내부 8080, 빈 결과·명령 실패·손상 결과를 테스트했다. 실제 세 러너의 탐색 함수를 fixture로 검증했다.

과거 XBEN-020 결과는 삭제하거나 성공으로 소급 변경하지 않는다. 공유 suite의 실행이 끝난 뒤 수정된 러너로 020을 별도 재시도하고, 그 실행이 `ssrf-demo-app`을 대상으로 했는지 확인해야 한다.

## 2. 실행 전에 잡을 수 있는 실패를 먼저 차단

숫자 옵션에 값 없이 `--timeout`이나 `--concurrency`만 쓰면 인자 파서가 `true`를 반환할 수 있었다. 이를 바로 숫자로 바꾸면 `1`이 되어 잘못된 명령이 정상 옵션으로 통과했다. 이제 문자열을 거쳐 숫자를 검증하므로 이런 입력을 거부한다.

동시성은 정수 1~5, 제한 시간은 양수이면서 JavaScript 타이머 범위를 넘지 않는 값으로 검사한다. 여러 러너를 동시에 띄울 때의 합계 5 이하는 운영자가 함께 관리해야 한다. 개별 러너의 검사만으로 전체 합계를 강제하지는 않는다.

Claude·MiniMax 러너는 patch-suite 프로세스의 실패 상태와 시작 오류도 검사한다. 패치가 실패했는데 실행 디렉터리를 만들고 compose나 유료 제공자 호출로 넘어가던 경로를 막았다. 테스트에서는 잘못된 옵션과 패치 실패 뒤 후속 작업이 시작되지 않는지 확인했다.

## 3. 다른 실행을 건드리지 않는 자원 정리

### 감시자의 실행 소유권

같은 문제를 다시 실행하면 이전 시도와 새 시도의 디렉터리가 함께 존재한다. 기존 감시자가 단순히 “이 문제의 가장 최근 실행”을 찾아 정리하면, 자신이 시작하지 않은 새 시도의 자원을 건드릴 수 있었다.

래퍼가 고유 토큰을 만들고 러너가 이를 `run-state`의 `wrapper_token`과 `runner_pid`로 기록하도록 했다. watchdog과 interrupt는 소유한 실행을 찾고, 태스크 잠금 아래에서 소유권을 다시 확인한다. 살아 있는 러너를 보호하며, 최종화할 때도 이미 확인한 정확한 실행 디렉터리를 사용한다.

### 이미지 정리 범위

이미지 ID 하나에는 여러 태그가 연결될 수 있다. ID를 강제로 제거하거나 전역 prune을 실행하면 다른 태스크가 사용하는 이미지까지 영향을 받을 수 있다.

공통 정리 함수는 해당 compose 프로젝트의 정확한 `Repo:Tag`를 수집해 중복을 제거하고, 강제 옵션 없이 삭제한다. 전역 image prune은 사용하지 않는다. native 러너의 빌드·시작 실패도 공통 최종화 경로에서 정리하며 `XBOW104_KEEP_IMAGES=1`은 존중한다.

### 종료 순서와 취소

native·MiniMax의 일부 timeout 경로는 비동기 컨테이너 정리가 끝나기 전에 실행 완료를 반환했다. 그러면 결과나 manifest를 확정한 후에도 정리 로그가 기록될 수 있었다. 이제 제한된 시간 안에서 kill·remove 완료를 기다린 뒤 결과를 확정한다.

native 스케줄러는 취소 신호를 받으면 대기열에서 새 태스크를 꺼내지 않는다. 취소된 실행이 남은 문제마다 불필요한 실패 기록을 만드는 일을 방지한다.

### 정상 네트워크를 장애로 오인하지 않기

doctor는 `xben` 이름의 네트워크가 있다는 이유만으로 고아 자원이라고 경고하지 않는다. 연결된 컨테이너가 있으면 사용 중인 상태로 보고, 비어 있으면 정리 후보로 표시한다. 조회 실패는 “비어 있음”이 아니라 “확인 불가”다. 이 진단은 자원을 자동 삭제하지 않는다.

## 4. headless 실행: 도구가 찾은 증거를 채점에서 놓치지 않도록 수정

### 증거가 있는데 실패할 수 있었던 이유

기존 headless 경로는 이벤트 구독을 만든 뒤 첫 사용자 요청 처리가 끝날 때까지 기다렸다. 그동안 실시간 방송 버퍼에 이벤트가 쌓였다. 버퍼 용량은 1,024개이므로 도구가 flag를 출력한 후 텍스트 이벤트가 대량 발생하면 앞의 `ToolFinished` 알림이 밀려날 수 있었다.

디스크 journal에는 도구 결과가 남아 있어도 headless 수신자가 해당 알림을 놓치면 성공을 인식하지 못할 수 있었다. 별도로 제한 시간의 시작점이 첫 요청 완료 뒤에 있어 오래 걸리는 초기 호출이 제한 밖에 놓였다. 수집한 도구 출력을 계속 연결하는 방식도 메모리 사용을 늘렸다.

### 변경된 판정 흐름

1. 첫 요청을 제출하기 전에 마감 시간을 설정한다.
2. 요청 실행, 이벤트 수신, 제한 시간 감시를 동시에 진행한다.
3. 시작·종료 알림만 믿지 않고 런타임의 활성 턴 수를 통해 유휴 상태를 확인한다.
4. 기록을 마무리한 뒤, 이번 실행 시작 시점 이후의 journal `ToolResult`로 최종 flag를 확인한다.

모델이 문장으로 주장한 flag는 도구 증거로 인정하지 않는다. 재개한 세션에 남아 있던 과거 flag도 이번 실행의 성공으로 세지 않는다. 이를 위해 시작 시점의 journal sequence를 기준점으로 사용한다.

### journal 읽기의 비용과 무결성

선택 visitor를 추가해 기록을 한 번 순회하면서 필요한 종류와 sequence 이후의 이벤트만 복원한다. 각 기록의 순서와 checksum을 검사하고, 선택한 외부 blob은 digest도 확인한다. 관련 없는 큰 transcript blob은 메모리에 읽어 들이지 않는다.

선택한 도구 이벤트에는 개별 크기 제한을 적용하고 콜백 처리 후 버린다. 전체 결과를 한 배열에 누적하거나 페이지마다 journal 처음부터 다시 읽지 않는다. 기존 일반 replay의 제한은 유지한다.

이벤트 폭주, 끝나지 않는 초기 요청, 과거 flag 제외, 큰 무관 blob, 크기·checksum·digest 경계를 검증했다. 다만 **런타임이 journal에 쓰기 전에 이미 잘라낸 도구 출력까지 복구하는 수정은 아니다.** 이 별도 문제는 프로젝트 평가의 미해결 항목으로 남겼다.

## 5. 점수·토큰·비용을 실제 기록에 맞게 집계

### 중간 오류와 최종 실패를 구분

이전 분류는 로그에 429나 스트림 재시도가 한 번이라도 있으면, 이후 정상 종료한 실행까지 제공자 장애로 제외할 수 있었다. 이제 해결 여부, 정상 종료와 timeout 같은 최종 상태를 먼저 반영하고 종료를 막은 제공자 오류를 구분한다.

정상적으로 회복한 재시도는 곧바로 인프라 장애가 아니다. 시간 내 풀지 못한 timeout도 유효한 평가 결과다. runtime fault의 채점 제외 정책은 유지하지만, 그 분류만으로 타깃 인프라가 원인이라고 단정하지 않는다.

### 0과 미측정을 구분

현재 런타임의 사용량은 `telemetry/usage.jsonl`에 기록되는데 일부 집계는 예전 로그 경로를 읽었다. 그 결과 사용량이 있어도 0으로 보일 수 있었다. 현재 사용량 파일을 우선 읽고 중복 집계를 피하도록 수정했다.

입력·출력 토큰이 존재하는데 total이 없거나 0인 과거 기록은 집계 시 합산한다. 원본 증거를 덮어쓰지 않는다. 측정되지 않은 도구·대기·shell 지표는 `null`로 표시한다. 알 수 없는 비용이 포함되면 전체 비용 역시 확정 숫자로 제시하지 않는다. “측정되지 않음”을 “문제 0건”으로 읽어서는 안 된다.

### 재시도와 캐시를 반영

공통 provider 보고서는 유효한 실행의 성공 수와 같은 범위의 분모를 사용한다. 비용·토큰 소비는 보존된 완료 시도 전체를 합산한다. 예를 들어 한 문제를 세 번 시도했다면 점수용 대표 결과와 세 번의 소비량은 서로 다른 집계 대상이다.

OpenAI 형식처럼 입력 토큰에 캐시 토큰이 이미 포함된 경우에는 중복 합산을 피한다. Claude의 별도 중복 렌더러도 공통 보고서 경로로 통합했다.

대표 실행 선택 정책이 전부 같아진 것은 아니다. XBOW 공통 summary/index/KPI는 문제별 최신 **유효** 실행을, provider 보고서는 최신 **완료** 실행을 선택한다. 뒤의 실행이 제외 대상이면 보고서 간 점수가 달라질 수 있으므로 이 차이를 문서에 명시했다.

### 실행 시간의 의미를 바로잡음

기존 `duration_s`는 일부 러너에서 빌드·시작 시간을 포함하고 종료 정리 포함 여부도 달랐다. 이를 “순수 solver 시간”이라고 설명한 문구가 부정확했다. 실제 측정 구간에 맞춰 실행 시도 경과 시간이라고 표기했다.

새로운 순수 추론 시간 수치를 만들어 낸 것은 아니다. 동시 실행의 시도 시간을 합한 값도 캠페인 전체의 실제 경과 시간과 다르다.

## 6. 실패 기록을 지우지 않고 보존

기존 정리는 좋은 결과를 남기는 과정에서 이전 실패나 재시도 기록을 삭제할 수 있었다. 그러면 장애 원인과 총소비량을 재구성하기 어려워진다. `pruneTaskRuns`는 호출 호환성을 유지하되 실행 이력을 삭제하지 않도록 바꿨다.

보존 대상과 보고서 대표 결과 선택은 구분한다. 과거에 이미 삭제된 증거는 이번 변경으로 복원되지 않는다. native의 `run-state`·harness·audit manifest 수집 체계가 Claude·MiniMax에 그대로 존재하는 것도 아니다. Claude는 별도의 raw transcript를 보존하며 읽기용 텍스트에는 축약이 있을 수 있다.

## 7. 빌드와 검증 경로를 저장소 계약에 맞춤

`dimage.ps1`에 runner 빌드 경로를 추가하고 runner → app → base 의존관계를 명시했다. 오래된 로컬 app 태그를 우연히 사용하는 일을 줄이기 위한 변경이다. default Docker builder와 직접 image store 로드를 사용하며 Rust 빌드 병렬도 제한을 유지한다. native의 setup도 이 래퍼를 통한다.

Node 실행은 `nverify.ps1`로 통일했다. 기본값은 제한된 Docker Node 24 검증이다. 실제 호스트 Docker CLI·Claude 인증이 필요한 러너에는 명시적인 `-HostNode` 경로를 제공하며, 안정 버전 Node 24인지 검사하고 인자를 배열 그대로 전달한다.

프로젝트 검증에서 오래된 `--resume` 요구를 현재 check의 독립된 새 `--run` 계약에 맞췄다. Node 테스트 진입점은 새 벤치마크 회귀 테스트도 실행하도록 확장했다. `npm run check`가 이미지 빌드 후 Docker TUI를 실행하는 계약은 유지했다.

## 8. 반복되는 인프라 보고를 줄이는 운영 기준

[RUNBOOK](../../benchmarks/xbow104/RUNBOOK.md)에 사전 점검, 전체 동시성 한도, 자원 소유권, 분류 기준과 보고 절차를 모았다. [HANDOFF](../../benchmarks/xbow104/HANDOFF.md)에는 다음 에이전트에게 그대로 전달할 프롬프트와 재개 명령을 넣었다.

운영 에이전트는 5분 간격으로 관찰하고, 정상 상태를 반복 보고하지 않는다. 이슈는 모델·태스크·실패 단계·오류 signature로 묶어 새 차단 문제, 악화, 증거 손실을 중심으로 보고한다. 보고에는 실제 오류와 근거 경로, 진행·채점에 미친 영향을 포함한다.

사용 중인 네트워크, 회복한 429, 유효한 timeout을 자동으로 인프라 장애라고 부르지 않는다. 실행 중에는 전역 prune, 광범위 삭제, Docker 재시작으로 문제를 덮지 않는다. 공유 suite 변경과 이미지 재빌드는 라이브 작업이 끝난 뒤 수행한다.

## 9. 변경 파일과 검증 근거

| 변경 위치 | 역할 / 관련 테스트 |
|---|---|
| `benchmarks/xbow104/target.mjs`, 세 provider 러너 | 타깃·endpoint 선택 / `test/xbow-target.test.mjs` |

| `src/main.rs`, `crates/ma-journal/src/lib.rs` | headless 증거·deadline·journal 선택 읽기 / 각 Rust 단위 테스트 |
| `evidence.mjs`, `kpi.mjs`, `build-results-index.mjs`, `benchmarks/lib/standard-report.mjs` | 분류·보존·통계 / `test/benchmark-metrics.test.mjs` |
| `scripts/dimage.ps1`, `docker-bake.hcl`, `scripts/nverify.ps1`, `scripts/verify-project.mjs` | 빌드·검증 계약 / PowerShell 래퍼 테스트 |

표에서 파일명만 표시한 XBOW 공통 모듈은 `benchmarks/xbow104/` 아래에 있다. 전체 작업 디렉터리에는 작업 시작 전부터 존재하던 변경도 있으므로 모든 git diff가 이번 개선에 속하는 것은 아니다.

앞선 코드 수정 완료 시 실제 실행한 검증은 Rust **188개 통과**, Node **50개 통과**, Rust fmt·clippy 통과, PowerShell check·dimage·nverify 테스트 통과다. 명령과 검증 범위는 [검증 기록](reliability-2026-09-05.md#verification)에 남겼다. 이번 보고서 작성 자체를 위해 전체 테스트를 다시 실행하지는 않았다.

타깃과 provider 관련 회귀 테스트는 fixture·mock을 사용했다. 실제 유료 모델이나 라이브 컨테이너를 호출하지 않았다. 이미지 의존관계는 mock과 bake 출력으로 확인했으며 새 release 이미지를 실제 빌드한 결과는 아니다.

## 10. 적용 상태와 남은 한계

수정은 작업 디렉터리에 반영되어 있다. 이미 실행 중인 프로세스에는 새 코드가 자동 반영되지 않는다. Rust headless 변경을 실사용하려면 라이브 작업 종료 후 `dimage.ps1`로 해당 이미지를 재빌드해야 한다. 이후 HANDOFF 절차에 따라 XBEN-020을 재시도한다. 커밋·푸시는 수행하지 않았다.

이번 작업으로 모든 잠재 장애가 사라졌다고 보장할 수는 없다. 실제 104개 실행은 아직 하지 않았으며, 외부 이미지·모델 제공자·Docker 상태에 따른 추가 실패는 실행 증거로 판단해야 한다.

벤치마크 밖의 핵심 에이전트 품질 문제도 남아 있다. 중첩 worker 생성의 권한·슬롯 정리, note 저장 실패 후 복구, journal 기록 전 도구 출력 축약, compaction의 의미 보존과 재개 정책 일치 문제는 [프로젝트 품질 평가](project-audit-2026-09-05.md)에 별도 기록했다. 이번 인프라 개선을 이 문제들까지 해결한 것으로 해석해서는 안 된다.

후속 운영에서는 **정확한 타깃, 실행별 소유권, 보존된 증거, 최종 상태에 따른 분류, 미측정의 명시**를 기준으로 판단한다. 이것이 실제 에이전트 실패와 실행 장치의 결함을 구분하는 근거다.

## 검증 실행 기록

대상: C:\workspace\minimal-agent, main 작업 디렉터리의 이번 수정 완료 상태.
아래는 이 세션에서 실제 실행한 결과다. 이전 문서의 통과 주장을 재사용하지 않았다.

| 검증 | 결과 |
|---|---|
| dbuild test --workspace --all-targets --quiet | exit0, 188 passed / 0 failed / 0 ignored |
| dbuild fmt --all -- --check | exit0 |
| dbuild clippy --workspace --all-targets -- -D warnings | exit0, 경고 없음 |
| nverify 기본 Node24 Docker gate | exit0, Node tests50/50 + verify-project + npm pack dry-run + verify-pack |
| test/check.test.ps1 | exit0, 이미지 빌드 후 fresh isolated run 계약 |
| test/dimage.test.ps1 | exit0, default builder와 runner→app→base 빌드 인자 mock |
| test/nverify.test.ps1 | exit0, Docker default/Node24 host 검사/literal argv/잘못된 버전 거부 |
| git diff --check | exit0 |
| 관련 벤치마크 Markdown 상대링크 확인 | 통과 |
| 독립 코드 리뷰 | target/lifecycle/headless 교차검토 및 발견된 경계 수정 후 차단 결함 없음 |

재실행 명령(저장소 루트 PowerShell):

```powershell
& ./scripts/dbuild.ps1 test --workspace --all-targets --quiet
$formatArgs = @('fmt', '--all', '--', '--check')
& ./scripts/dbuild.ps1 @formatArgs
$lintArgs = @('clippy', '--workspace', '--all-targets', '--', '-D', 'warnings')
& ./scripts/dbuild.ps1 @lintArgs
& ./scripts/nverify.ps1
& ./test/check.test.ps1
& ./test/dimage.test.ps1
& ./test/nverify.test.ps1
```

PowerShell 인자 파싱에서 Cargo의 `--` 구분자가 유실되지 않도록 Rust 후행 인자는 배열로
전달했다. Node 테스트는 fixture/tempdir/mock으로 실제 러너 함수의 경계를 검증한다.
진행 중 타깃이나 유료 provider를 테스트 대상으로 호출하지 않는다.

추가 재현·검증:

- XBEN-020 공개앱 선택: compose 서비스 순서 양쪽, JSON 배열/NDJSON, 세 실제 discovery 함수.
- TCP/UDP, 내부8080, 실패/손상/누락 compose 결과, bare numeric 옵션 및 patch 실패.
- 정상 provider 재시도, 미측정 KPI, 재시도 소비·캐시·분모, 시간구간 문구.
- watchdog의 이전/현재 소유권, 취소 후 배정 중단, timeout 정리 순서, 모든 종료의 이미지 정리.
- headless 초기 호출 deadline, 방송 overflow, 과거 resumed flag 제외, 큰 무관 journal blob.
- journal watermark와 선택 visitor의 byte/sequence/checksum/blob 검증.

수행하지 않은 검증:

- 전체104개 실벤치 재실행 또는 XBEN-020 실타깃 재시도
- release 이미지 실제 빌드, 실제 브라우저/interactive TUI smoke
- 라이브 산출물 재생성 또는 과거 삭제 evidence 복원

현재 라이브 러너·컨테이너·외부 suite를 변경하지 않았고 새 벤치마크를 시작하지 않았다.
이미지 의존관계는 bake --print와 mock으로 검증했다. 새 Rust 바이너리의 실사용 반영은
공유 suite의 라이브 작업이 종료한 뒤 dimage로 이미지를 다시 빌드해야 한다.
커밋/푸시/새 브랜치/워크트리/PR을 만들지 않았다.
