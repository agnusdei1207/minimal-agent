# ADR-0003: Shell Execution Model and Interactive Terminal Primitives

- Status: Accepted
- Created: 2026-08-31 +09:00
- Updated: 2026-09-05 +09:00
- Version target: 0.112.0
- Repository: `agnusdei1207/minimal-agent`
- Relation: ADR-0001의 최소 코어 철학과 ADR-0002의 승인된 교전 환경을 잇는다. 대화형 작업(`sudo`, `nc`, `gdb`, REPL) 및 장기 실행 작업(스캔, 리스너)을 처리하기 위한 쉘 실행 계층의 구조적 설계를 규정한다.
- 통합·대체: 이 ADR은 기존 `ADR-0003-interactive-shell-model-and-methodology-library.md`(Proposed) 초안을 통합·대체한다. 그 초안이 검토했던 대안·배경 중 유의미한 부분은 본 문서 §2와 §5(Considered / Rejected alternatives)에 흡수했다.
- 개정 메모(2026-09-05): 구현 단계에서 §3.1의 `shell` 툴 `stdin` 파라미터 확장안은 **기각**되었다. 기존 `bash` 도구의 스키마/동작은 그대로 보존하고, 대신 대화형/지속형 시나리오를 OS 네이티브 tmux에 위임하는 **범용 `tmux` 도구를 정식으로 추가**했다(커밋 f3cf99d, §3.1 참조). 이로써 코어는 PTY/IPC를 재구현하지 않고 얇은 패스스루만 유지한다.

---

## 1. 한 문장 결정

`minimal-agent`는 외부 PTY 데몬이나 무거운 터미널 에뮬레이션 계층을 Rust 코어에 구축하지 않고, (1) 기존 `bash` 도구는 무오염 일회성 실행 규약을 그대로 유지하며, (2) 대화형/지속형 세션(PTY 확보, 백그라운드 리스너, REPL stdin 주입)은 OS 네이티브 tmux를 그대로 호출하는 **범용 `tmux` 패스스루 도구**에 위임하고, (3) 복잡한 프로토콜 조작은 Script-First(`pwntools`, `pexpect`) 패턴과 FIFO 파이프에 위임한다.

## 2. 배경과 핵심 고민 (Design Dilemma)

### 2.1 기존 접근(별도 PTY 데몬 모델)의 한계
모의해킹/CTF 에이전트 개발에서 대화형 프로세스(예: `sudo` 비밀번호 입력, `nc` 기반 인터랙티브 챌린지, `gdb`, 리버스 쉘)를 다루기 위해 흔히 채택되는 방식은 **"별도 PTY 데몬 + Unix Domain Socket(UDS) IPC + 센티널(Sentinel) 파싱"** 구조다.

```text
[과거 PTY 데몬 모델의 과도한 복잡도]
Agent Core ──(UDS/JSON-RPC)──> Daemon ──(openpty)──> Target Shell
                                  │
      ┌───────────────────────────┴───────────────────────────┐
      │ • UUID 센티널 주입: echo "__START__"; cmd; echo "__END__" │
      │ • 4단계 상태머신 (Probe -> Spawn -> stty -> Validate)   │
      │ • 정규식 기반 프롬프트 감지 ($ / # / (gdb))            │
      │ • ANSI 이스케이프 시퀀스 실시간 정제 및 링버퍼           │
      └───────────────────────────────────────────────────────┘
```

이 모델은 실전 환경에서 심각한 구조적 취약점을 드러냈다:
1. **과도한 프로세스적 복잡도**: IPC 통신, 소켓 파일 수명주기, FD 누수, 좀비 프로세스 정리 등 런타임 부담이 기하급수적으로 증가함.
2. **센티널 파싱 취약성**: 입력을 능동적으로 소비하거나 서브쉘을 띄우는 프로그램에서 센티널 토큰이 왜곡되거나 누락되어 에이전트가 타임아웃까지 블로킹됨.
3. **상태머신 경직성**: 타깃 환경(컨테이너, BusyBox, Windows 등)의 사소한 차이에도 쉘 승격 상태 전이가 실패함.
4. **플랫폼 종속성**: POSIX `openpty` 전용으로 설계되어 크로스플랫폼(Windows/Linux) 지원이 어려움.

### 2.2 리버스 셸의 "덤프 셸" 문제 (대화형이 필요한 이유)
리버스 셸을 `nc`로 받으면 이는 제어 tty가 없는 **"덤프 셸(dumb shell)"**이다 — job control·`sudo`·에디터·전체화면 프로그램·프롬프트가 깨진다. 전통적 "full TTY 업그레이드"는 로컬 터미널을 사람이 직접 raw 모드로 돌리는(`Ctrl-Z` → `stty raw -echo` → `fg`) 순차 조작을 요구하는데, 이는 **이산 턴(Turn)으로 도구를 호출하는 LLM**에게는 표현하기 어렵다. 이 로컬 raw-mode "춤"이 필요한 유일한 이유는 리스너가 덤프 셸이기 때문이며, **리스너를 실제 터미널(tmux 세션) 안에서 띄우면** 로컬 raw 조작이 사라지고 원격에만 `pty.spawn`을 붙이면 된다(대상에 `socat`이 있으면 완전한 pty를 한 번에 넘길 수 있다). 즉 "대화형 세션 문제"의 본질은 코어가 아니라 **실제 tty를 가진 세션 관리자**를 확보하는 것이며, OS가 이미 tmux로 그것을 제공한다.

### 2.3 핵심 질문
> **"LLM 에이전트에게 필요한 터미널 상호작용의 본질은 무엇이며, OS의 터미널/프로세스 관리자를 에이전트 프레임워크가 다시 구현해야 하는가?"**

LLM은 사람처럼 키보드를 타건하고 모니터를 응시하는 존재가 아니라, **이산적인 턴(Turn) 단위로 도구를 호출하는 모델**이다. 프레임워크가 터미널 에뮬레이터를 직접 흉내 내는 것은 에이전트의 유연성을 오히려 제한하고 버그의 온상이 된다.

## 3. 결정 내용

### 3.1 범용 `tmux` 도구 정식 추가 (구현 채택안 · `shell` stdin 확장은 기각)

[`crates/ma-runtime/src/tools.rs`](file:///C:/workspace/minimal-agent/crates/ma-runtime/src/tools.rs)에 별도의 **`tmux` 도구**를 추가한다. 기존 `bash` 도구는 변경 없이 유지한다(스키마·동작 보존). `stdin` 파라미터 확장, `bash`→`shell` 리네임, 공용 세션 관리자 등 검토됐다 기각·대체된 대안은 §5를 참조한다.

- **도구 인터페이스**: 최소·범용 패스스루. 특정 서브커맨드로 스키마를 좁히지 않는다(확장성).
  ```json
  {
    "name": "tmux",
    "parameters": {
      "type": "object",
      "properties": { "args": {"type": "string"} },
      "required": ["args"]
    }
  }
  ```
- **동작 원리**:
  - `args` 문자열을 `bash`와 **동일한 일회성 셸 메커니즘**(동일 spawn/타임아웃/출력 바운드/취소/에러 규약)으로 `tmux <args>` 형태로 실행한다. 파이프·리다이렉션이 그대로 동작한다(`capture-pane -p -t s | tail -n 50`).
  - Rust 코어는 PTY 에뮬레이터/IPC 파이프를 재구현하지 않는다. PTY·세션 상태·수명주기는 전적으로 tmux가 소유한다.
  - 이 얇은 도구 하나로 §3.2의 네 가지 핵심 패턴(세션 생성/키 주입/화면 캡처/세션 정리)이 그대로 실현된다.

---

### 3.2 복합 대화형 세션의 OS 네이티브 도구 위임 (Doctrine)

지속적인 세션 유지, 백그라운드 리스너 대기, 실시간 프롬프트 조작이 필요한 복합 시나리오는 Rust 코어에 새 메커니즘을 추가하지 않고 **OS 표준 유틸리티**를 활용하도록 프롬프트와 doctrine으로 가이드한다.

#### ① `tmux`를 활용한 제로-코드(Zero-Code) PTY 세션 (4대 패턴)
리눅스/컨테이너 환경에서 검증된 `tmux`를 `tmux` 도구로 제어한다.
- 세션 생성: `tmux new-session -d -s exp "nc -lvnp 4444"`
- 키 입력 주입: `tmux send-keys -t exp "whoami" Enter`
- 화면 캡처: `tmux capture-pane -p -t exp` (깨끗한 텍스트 렌더링)
- 세션 정리: `tmux kill-session -t exp`

#### ② Script-First 패턴 (`pwntools`, `pexpect`)
복잡한 프로토콜 핸드셰이크, 바이너리 익스플로잇, 버퍼오버플로우 조작은 터미널 타이핑 대신 [`workspace`](file:///C:/workspace/minimal-agent/crates/ma-runtime/src/tools.rs)로 스크립트를 작성하여 원샷 실행한다.
- `pwntools`가 소켓 I/O, PTY 할당, `recvuntil` 대기, 페이로드 전송을 완벽히 처리함.
- 작성된 스크립트는 워크스페이스에 아티팩트로 영구 보존되어 완벽한 재현성을 제공함.

#### ③ Unix FIFO / 백그라운드 파일 리다이렉션
추가 의존성 없는 순수 POSIX 환경에서는 전통적인 파일 리다이렉션 패턴을 사용한다.
- `mkfifo /tmp/in; cmd < /tmp/in > /tmp/out 2>&1 &`
- `echo "payload" > /tmp/in`
- `tail -n 30 /tmp/out`

#### 세션 base 계약 (전제)
위 패턴이 성립하려면 런타임 base 이미지에 `tmux`(세션·화면 캡처)와 `socat`(완전 pty 업그레이드)이 존재해야 한다. 이는 doctrine 권고가 아니라 **base 이미지 계약**이며, 없으면 §3.1~§3.2가 성립하지 않는다.

---

### 3.3 팀 구조를 활용한 장기 작업 격리

장시간 실행되는 스캔(`nmap -p-`), 브루트포스(`gobuster`), 상시 대기 리스너 등은 메인 에이전트의 턴 루프를 블로킹하지 않고, ADR-0001의 **2-Depth Worker 에이전트**에게 위임한다.
- `main`은 `team create`로 전담 worker를 생성하고 즉시 다른 분석으로 복귀.
- worker는 작업 완료 시 `team send kind=insight`로 핵심 결과만 main에게 보고.

## 4. 하지 않는 것 (Anti-patterns & Non-goals)

1. **별도 IPC 데몬 프로세스 구축 금지**: UDS 소켓, 백그라운드 리스너 데몬, 전용 클라이언트 라이브러리를 만들지 않는다.
2. **문자열 기반 센티널 주입 금지**: 명령 문자열 앞뒤로 난수 UUID를 래핑하는 불안정한 기법을 사용하지 않는다.
3. **가상 터미널 에뮬레이터 재구현 금지**: ANSI 정제, 링버퍼, 커서 상태 추적을 Rust 코어로 짊어지지 않는다.
4. **전역 세션 오염 허용 금지**: 단일 프로세스 공간 내에서 전역 쉘 환경변수나 디렉터리 상태를 공유하여 에이전트 간 경계를 무너뜨리지 않는다. 세션 격리가 필요하면 세션명을 run-id로 네임스페이스(`ma-<runid>-<name>`)하여 고아 세션을 식별·수확한다.

## 5. Considered / Rejected alternatives (검토·기각된 대안)

병합 전 두 초안이 검토했던 대안들을 이력 보존을 위해 정리한다. 최종 채택안은 §3(범용 `tmux` 패스스루 도구 + Zero-Code tmux 4대 패턴)이다.

1. **`shell`/`bash` 도구에 `stdin` 파라미터 추가 (기각).** 일회성 stdin 일괄 전송(`sudo -S`, 사전 구성된 `nc` 질의/응답)에는 충분하지만, **지속형 세션·백그라운드 리스너·턴을 가로지르는 REPL 상호작용**은 여전히 표현하지 못한다. 기존 `bash` 도구 스키마/불변식을 건드리는 부담 대비 이득이 작다. 결국 필요한 것은 상태를 가진 세션 관리자이며, 그것은 OS가 이미 tmux로 제공한다.
2. **`bash`→`shell` 리네임 (기각).** 도구명을 바꿔 의미를 확장하는 것은 실익 없이 기존 스키마/동작 계약과 프롬프트 자산만 흔든다. `bash`의 무오염 일회성 계약을 그대로 두고, 대화형은 별도 `tmux` 도구로 직교하게 분리한다.
3. **공용 책상(shared named session) + 단일 기록자 모델 (대체됨).** 하나의 이름 붙은 tmux 세션을 팀 공유 자원으로 두고 여러 에이전트가 직접 attach해 "한 번에 한 명만 타이핑"하며 조종간을 팻말처럼 넘기는 안. 단일 기록자·run-id 네임스페이스·자동 정리·자원 상한을 런타임이 강제하는 설계였다. 범용 `tmux` 패스스루가 세션 생성/키 주입/캡처/정리를 이미 포괄하므로, 공유·기록권 조정 같은 무거운 런타임 관리 계층은 채택하지 않았다(필요 시 §4의 run-id 네임스페이스 관례로 충분). 세션 IPC를 팀 버스로 오해하지 않는 것도 같은 이유다 — 캡처 출력(최대 128 KiB)을 4 KiB 팀 메시지(ADR-0001 §6.3)로 중계하면 경계에서 잘리므로, 화면은 세션에서 직접 읽고/파일로 넘기며 팀 버스는 신호용으로만 쓴다.
4. **방법론 라이브러리/스킬 전용 접근을 이 ADR에 결합 (범위 분리).** 초안은 shell 모델과 함께 "자율 참조용 공격 방법론 카드(19종) 온디스크 라이브러리"를 같은 ADR에 묶었다. 본 ADR은 **쉘 실행/터미널 프리미티브**에 범위를 한정한다. 온디스크 스킬/doctrine 자산은 코어 도구 표면 결정이 아니라 doctrine·이미지 자산 계약의 문제이므로, 이 ADR의 결정 범위에서 분리한다.
5. **PTY 데몬 + UDS/RPC 제어평면 (기각).** 수천 줄 코어·크로스플랫폼 부담. tmux가 이미 검증된 형태로 제공한다. (`../pentesting`은 이 무거운 경로를 택했고, 본 저장소는 clean-room 경량 경로를 택한다 — reference-only, 포팅하지 않음.)
6. **세션 소유 worker + 형제가 RPC로 중계 (기각).** 모든 I/O에 모델 턴이 끼어 느리고, 4 KiB 팀 메시지 경계에서 화면이 잘린다. 각 에이전트가 tmux 세션에서 직접 읽는 편이 더 가볍고 자율적이다.
7. **방법론을 프롬프트에 전부 굽기 (기각).** a-z 지식을 매 턴 고정 비용으로 얹는다. 온디스크 라이브러리 + 선택적 읽기가 토큰 효율·자율성에서 우위다.
8. **개별 전용 공격 도구 표면 세분화 (기각) — "3-Layer Golden Rule".** `nmap_scan`, `sqlmap_run`, `gdb_disasm`, `jwt_forge` 같은 공격 기능별 Function Tool 수십 개를 등록하는 대신 `bash`/`tmux`·`workspace`·`team` 범용 도구 체제를 유지한다.
   - 매 턴 수천 토큰 낭비 방지: 15~20개 전용 도구 스키마는 매 턴 3,000~6,000 토큰을 잠식하나, 범용 도구는 수백 토큰으로 끝나 문맥 예산을 증거와 기억(`brief.md`)에 온전히 배분한다.
   - 파이프라인·조합성: 실전은 `nmap ... | grep open | cut ... | xargs ffuf ...` 같은 파이프라이닝·서브셸·즉석 파이썬 원라이너의 유기적 결합이 본질이며, 도구를 쪼개면 파이프 1개당 턴 수가 폭발한다.
   - LLM 친화력: 프론티어 LLM은 임의 커스텀 스키마보다 표준 Bash/Python에 압도적으로 최적화되어 스키마 오류를 내지 않는다.
   - 런타임 디커플링: 신규 기법·도구는 Rust 재컴파일 없이 Docker 이미지(`apt`/`pip`)나 런타임 자율 조달로 대응한다.
   - 결론: 도구 인터페이스(Rust 코어)는 극도로 최소화, 실행 환경(Docker)은 풍부하게 사전 완비, 지식 베이스(Skills)는 온디스크 분리 — 이 3계층 분리가 최적이다.
